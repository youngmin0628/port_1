# 벤치마크

## 측정 환경

| 항목 | 값 |
|---|---|
| CPU | AMD Ryzen 5 5600X (6C/12T) |
| RAM | 16GB |
| OS | Windows 10 Pro |
| 인프라 | Docker Desktop, MySQL 8.4.10 컨테이너 |
| JVM | Temurin 21.0.11 (Gradle toolchain으로 확보) |
| 앱 실행 | 로컬 (`gradlew bootRun`), 컨테이너 아님 |

**한계.** 앱, MySQL 컨테이너, k6가 모두 같은 머신에서 돈다.
k6가 CPU를 쓰면 그만큼 앱과 DB가 못 쓴다.
따라서 절대 수치는 의미가 없고 **Phase 간 상대 비교만 유효하다.**
다른 환경에서 측정한 수치와 이 표를 나란히 놓지 않는다.

## 측정 조건

목적이 다르므로 조건도 다르다. 두 조건의 수치를 섞어 비교하지 않는다.

### 정합성 (JUnit + Testcontainers)

| 항목 | 값 |
|---|---|
| 쿠폰 총 수량 | 100 |
| 요청 스레드 수 | 1000 (`ExecutorService` + `CountDownLatch`) |
| 측정 대상 | 최종 발급 건수 |
| 통과 기준 | 정확히 100건 |

### 부하 (k6)

| 항목 | 값 |
|---|---|
| 쿠폰 총 수량 | 1,000,000 (30초 안에 소진되지 않도록) |
| VU | 200 |
| duration | 30s |
| 측정 대상 | TPS, p95, p99 |
| 사전 조건 | `docker compose down -v`로 DB 초기화 |

수량을 100으로 두고 부하를 걸면 첫 수십 밀리초에 전량이 소진되고 남은 시간은
전부 품절 응답이다. 그러면 TPS와 p99가 발급 경로가 아니라 거절 경로를 재게 되어
Phase 간 비교가 무의미해진다.

`count()` 비용은 누적 행 수에 비례하므로 매 측정 전 DB를 비운다.

### 공통

| 항목 | 값 |
|---|---|
| HikariCP `maximum-pool-size` | 10 |
| `innodb_flush_log_at_trx_commit` | 1 (기본값) |
| `innodb_buffer_pool_size` | 128MB (기본값) |
| `innodb_lock_wait_timeout` | 50 (기본값, Phase 2에서 조정 예정) |
| 기본 격리 수준 | REPEATABLE READ |

`innodb_flush_log_at_trx_commit`을 2로 바꾸면 TPS가 크게 오르지만
그건 개선이 아니라 내구성을 팔아 얻은 수치다. 기본값을 지킨다.

## 오버셀 (정합성 조건)

쿠폰 100장에 1000 스레드가 동시 요청한 결과다. 예외는 두 경우 모두 0건이므로
DB 오류가 섞이지 않은 순수한 오버셀이다.

| 커넥션 풀 크기 | 발급 건수 | 초과 | 테스트 |
|---|---|---|---|
| 10 | 107 | +7 | `CouponIssueConcurrencyTest` |
| 50 | 126 | +26 | `CouponIssueConcurrencyLargePoolTest` |

**오버셀 규모의 상한은 커넥션 풀 크기가 정한다.**
`count()`와 `save()` 커밋 사이의 창에서 겹칠 수 있는 트랜잭션 수가
풀 크기로 제한되기 때문이다. 1000 스레드를 던져도 DB에서 실제로 경합하는 것은
풀 크기만큼이다.

초과분이 풀 크기에 정비례하지는 않는다(풀 10 → 7, 풀 50 → 26).
풀 크기는 동시에 겹칠 수 있는 **최대치**이고, 실제로 재고 경계 시점에
창 안에 들어와 있던 트랜잭션은 그보다 적었다는 뜻이다.

### 원인 — read-modify-write

1. **read.** 트랜잭션 A와 B가 각각 `countByCouponId()`로 발급 수를 읽는다.
   MySQL 기본 격리 수준 REPEATABLE READ에서 각 트랜잭션은 첫 읽기 시점의
   스냅샷을 보므로, 거의 동시에 시작한 A와 B는 **같은 값(예: 99)** 을 읽는다.
2. **modify.** 둘 다 `99 >= 100`이 거짓이므로 발급 조건을 통과한다.
   상대방이 곧 발급할 것이라는 정보가 어디에도 없다.
3. **write.** 둘 다 insert하고 커밋한다. 발급 수는 101이 된다.

읽은 값이 쓰기 시점까지 유효하다는 보장이 없는데 그 값을 근거로 쓰기를 결정한 것이
문제다. 읽기와 쓰기가 하나의 원자적 단위가 아니다.

## 결과

| Phase | 방식 | TPS | p95 | p99 | 오버셀 | 비고 |
|-------|------|-----|-----|-----|--------|------|
| 1 | 나이브 (`count()` → 비교 → `save()`, 락 없음) | 939 | 268ms | 452ms | +7건 | avg 212ms, 발급 28,359건, 품절 0건 |

Phase 0은 발급 로직이 없어 측정 대상이 아니다.

**오버셀 수치와 지연 수치는 조건이 다르다.** 같은 행에 있지만 같은 실행의 결과가 아니다.
오버셀(+7)은 정합성 조건(수량 100, 1000 스레드, 풀 10, Testcontainers)에서,
TPS와 지연은 부하 조건(수량 100만, VU 200, 30s, compose MySQL)에서 측정했다.

품절이 0건이므로 30초 동안 수량이 소진되지 않았고, 모든 요청이 실제 발급 경로를 탔다.

### 측정 중 관찰한 것

**나이브 구현의 지연은 시간이 갈수록 나빠진다.** 부하 테스트 동안 발급 행이 계속
쌓이므로 `countByCouponId()`가 훑는 행 수가 0에서 28,359까지 증가한다.
표의 수치는 그 구간의 평균이다. p99가 452ms로 p95(268ms)의 1.7배인 것도
이 성질과 무관하지 않다. Phase 3에서 재고 관리를 Redis로 옮기면 이 성질 자체가 사라진다.

**연결 단계 실패 39건 (0.13%).** `dial tcp 127.0.0.1:8080: connectex: No connection
could be made because the target machine actively refused it`.
관측된 경고는 모두 테스트 시작 직후에 찍혔다. 200 VU가 동시에 연결을 열 때
Tomcat의 accept 백로그가 넘쳐 RST가 나간 것이며 애플리케이션 오류가 아니다.
앱 로그에 예외가 없고, DB 행 수(28,359)가 `coupon_issued`와 정확히 일치하며,
`28,359 + 39 = 28,398` = 총 요청 수로 맞는다. 즉 앱은 받은 요청을 전부 처리했다.

램프업을 넣거나 `server.tomcat.accept-count`를 올리면 없앨 수 있지만 그대로 둔다.
선착순 쿠폰은 원래 모두가 동시에 몰리는 시나리오이고, Phase 2 이후도 같은 조건으로
측정하므로 비교에는 영향이 없다.
