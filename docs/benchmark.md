# 벤치마크

## 측정 환경

| 항목 | 값 |
|---|---|
| CPU | AMD Ryzen 5 5600X (6C/12T) |
| RAM | 16GB |
| OS | Windows 10 Pro |
| 인프라 | Docker Desktop, MySQL 8.4.10 컨테이너 |
| JVM | Temurin 21.0.11 (Gradle toolchain으로 확보) |
| 앱 실행 | 로컬 (`gradlew bootRun`), 컨테이너 아님 |

**한계.** 앱, MySQL 컨테이너, k6가 모두 같은 머신에서 돈다.
k6가 CPU를 쓰면 그만큼 앱과 DB가 못 쓴다.
따라서 절대 수치는 의미가 없고 **Phase 간 상대 비교만 유효하다.**
다른 환경에서 측정한 수치와 이 표를 나란히 놓지 않는다.

## 측정 조건

목적이 다르므로 조건도 다르다. 두 조건의 수치를 섞어 비교하지 않는다.

### 정합성 (JUnit + Testcontainers)

| 항목 | 값 |
|---|---|
| 쿠폰 총 수량 | 100 |
| 요청 스레드 수 | 1000 (`ExecutorService` + `CountDownLatch`) |
| 측정 대상 | 최종 발급 건수 |
| 통과 기준 | 정확히 100건 |

### 부하 (k6)

| 항목 | 값 |
|---|---|
| 쿠폰 총 수량 | 1,000,000 (30초 안에 소진되지 않도록) |
| VU | 200 |
| duration | 30s |
| 측정 대상 | TPS, p95, p99 |
| 사전 조건 | `docker compose down -v`로 DB 초기화 |

수량을 100으로 두고 부하를 걸면 첫 수십 밀리초에 전량이 소진되고 남은 시간은
전부 품절 응답이다. 그러면 TPS와 p99가 발급 경로가 아니라 거절 경로를 재게 되어
Phase 간 비교가 무의미해진다.

`count()` 비용은 누적 행 수에 비례하므로 매 측정 전 DB를 비운다.

### 공통

| 항목 | 값 |
|---|---|
| HikariCP `maximum-pool-size` | 10 |
| `innodb_flush_log_at_trx_commit` | 1 (기본값) |
| `innodb_buffer_pool_size` | 128MB (기본값) |
| `innodb_lock_wait_timeout` | 50 (기본값, Phase 2에서 조정 예정) |
| 기본 격리 수준 | REPEATABLE READ |

`innodb_flush_log_at_trx_commit`을 2로 바꾸면 TPS가 크게 오르지만
그건 개선이 아니라 내구성을 팔아 얻은 수치다. 기본값을 지킨다.

## 정합성 매트릭스

각 방식이 **무엇을 막는 장치인지**를 두 시나리오로 갈라 본 것이다.
둘 다 쿠폰 100장, 1000 스레드, 커넥션 풀 10에서 측정했다.

| 방식 | 재고 경합 (유저 1000명 × 1회) | 중복 발급 (유저 1명 × 1000회) |
|---|---|---|
| 나이브 (락 없음, 제약 없음) | 107건 — 실패 | 109건 — 실패 |
| unique 제약 단독 | 108건 — 실패 | **1건 — 통과** |
| 비관적 락 | **100건 — 통과** | 제약 없이는 실패 |
| 낙관적 락 | **100건 — 통과** | 제약 없이는 실패 |

**대각선으로 갈린다. 락과 unique 제약은 대체재가 아니다.**

`(coupon_id, user_id)` unique 제약을 넣은 뒤에도 재고 경합 테스트는 108건으로
그대로 실패한다. 유저가 전부 달라 제약에 걸리는 행이 하나도 없기 때문이다.
반대로 락은 재고를 지키지만 같은 유저가 여러 장 받는 것을 막지 않는다.

실서비스에는 둘 다 필요하다.

중복 발급 시나리오에서 제약 없이 109건이 나온 것은 중복이면서 동시에 오버셀이기도 하다.

## 오버셀 규모와 커넥션 풀 (나이브)

| 커넥션 풀 크기 | 발급 건수 | 초과 | 테스트 |
|---|---|---|---|
| 10 | 107 | +7 | `NaiveStockRaceTest` |
| 50 | 126 | +26 | `NaiveStockRaceLargePoolTest` |

**오버셀 규모의 상한은 커넥션 풀 크기가 정한다.**
`count()`와 `save()` 커밋 사이의 창에서 겹칠 수 있는 트랜잭션 수가
풀 크기로 제한되기 때문이다. 1000 스레드를 던져도 DB에서 실제로 경합하는 것은
풀 크기만큼이다.

초과분이 풀 크기에 정비례하지는 않는다(풀 10 → 7, 풀 50 → 26).
풀 크기는 동시에 겹칠 수 있는 **최대치**이고, 실제로 재고 경계 시점에
창 안에 들어와 있던 트랜잭션은 그보다 적었다는 뜻이다.

### 원인 — read-modify-write

1. **read.** 트랜잭션 A와 B가 각각 `countByCouponId()`로 발급 수를 읽는다.
   MySQL 기본 격리 수준 REPEATABLE READ에서 각 트랜잭션은 첫 읽기 시점의
   스냅샷을 보므로, 거의 동시에 시작한 A와 B는 **같은 값(예: 99)** 을 읽는다.
2. **modify.** 둘 다 `99 >= 100`이 거짓이므로 발급 조건을 통과한다.
   상대방이 곧 발급할 것이라는 정보가 어디에도 없다.
3. **write.** 둘 다 insert하고 커밋한다. 발급 수는 101이 된다.

읽은 값이 쓰기 시점까지 유효하다는 보장이 없는데 그 값을 근거로 쓰기를 결정한 것이
문제다. 읽기와 쓰기가 하나의 원자적 단위가 아니다.

## 결과

| Phase | 방식 | 스키마 | TPS | p95 | p99 | 오버셀 | 발급 |
|-------|------|--------|-----|-----|-----|--------|------|
| 1 | 나이브 (`count()` → 비교 → `save()`, 락 없음) | V1 | 939 | 268ms | 452ms | +7건 | 28,359 |
| 2 | 나이브 (재측정) | V1~V3 | 819 | 304ms | 529ms | +8건 | 24,734 |
| 2 | 비관적 락 (`SELECT FOR UPDATE`) | V1~V3 | **218** | 1.05s | 1.29s | **0건** | 6,644 |
| 2 | 낙관적 락 (`@Version` + 재시도) | V1~V3 | **114** | 4.80s | 7.09s | **0건** | 3,546 |

Phase 0은 발급 로직이 없어 측정 대상이 아니다.

**오버셀 수치와 지연 수치는 조건이 다르다.** 같은 행에 있지만 같은 실행의 결과가 아니다.
오버셀은 정합성 조건(수량 100, 1000 스레드, 풀 10, Testcontainers)에서,
TPS와 지연은 부하 조건(수량 100만, VU 200, 30s, compose MySQL)에서 측정했다.

품절은 모든 측정에서 0건이다. 30초 동안 수량이 소진되지 않았고 모든 요청이
실제 발급 경로를 탔다는 뜻이다.

**Phase 2 비교의 기준선은 941이 아니라 819다.** 스키마가 달라졌기 때문에
비관적·낙관적 락은 같은 스키마에서 잰 나이브 재측정값과 비교해야 한다.

### 정합성의 대가

| 방식 | TPS | 나이브(819) 대비 | p99 | 오버셀 |
|---|---|---|---|---|
| 나이브 | 819 | — | 529ms | +8건 |
| 비관적 락 | 218 | **-73%** | 1.29s | 0건 |
| 낙관적 락 | 114 | **-86%** | 7.09s | 0건 |

Phase 2가 확인해야 했던 것이 이 표다.
**오버셀을 0으로 만드는 대가로 처리량의 4분의 3에서 6분의 5를 잃었다.**
Phase 3에서 Redis를 쓰는 이유가 여기에 있다.

### 측정 중 관찰한 것

**낙관적 락이 비관적 락보다 2배 느리다.** 통념과 반대 방향이다.

이 부하 테스트는 200 VU가 **전부 같은 쿠폰 한 행**을 두드린다.
낙관적 락은 매 요청이 `coupon.version`을 갱신하므로 사실상 모든 커밋이 충돌한다.
충돌하면 트랜잭션을 버리고 처음부터 다시 하므로, 경합이 심할수록
"이미 한 일을 버리는 비용"이 쌓인다. 최대 응답시간이 12.18초까지 벌어진 것이 그 결과다.

정합성 테스트에서도 같은 성질이 보인다. 1000 요청으로 100장을 발급하는 데
**재시도가 808회** 필요했다. 요청당 평균 1.8회 DB 왕복이다.

낙관적 락은 충돌이 드물 때 쓰는 기법이다. 선착순 쿠폰은 정의상 충돌이 잦으므로
애초에 맞지 않는 자리였다. 그걸 수치로 확인한 것이 이 Phase의 소득이다.

**unique 제약은 공짜가 아니다.** 나이브 구현을 같은 코드로 두 번 쟀는데
스키마만 바뀌었을 뿐인데 TPS가 941에서 819로 13% 떨어졌다.
유력한 원인은 `(coupon_id, user_id)` unique 인덱스다 — insert마다 인덱스를 하나 더
갱신하고 유일성까지 검사한다.

단일 측정이므로 13%를 단정하지는 않는다. 다만 **정합성 장치는 락이든 제약이든
쓰기 경로에 비용을 붙인다**는 방향은 분명하다.

**나이브 구현의 지연은 시간이 갈수록 나빠진다.** 부하 테스트 동안 발급 행이 계속
쌓이므로 `countByCouponId()`가 훑는 행 수가 0에서 2만여 건까지 증가한다.
표의 수치는 그 구간의 평균이다. Phase 3에서 재고 관리를 Redis 카운터로 옮기면
이 성질 자체가 사라진다.

**연결 단계 실패가 매 측정에서 0.1~2% 발생한다.**
`dial tcp 127.0.0.1:8080: connectex: No connection could be made...`
애플리케이션 오류가 아니라 200 VU가 동시에 연결을 열 때 Tomcat accept 백로그가
넘쳐 RST가 나간 것이다. 자세한 근거는 `docs/known-issues.md`에 있다.

락 구현에서 비율이 높아진 것(1.45%, 2.15%)은 응답이 느려져 연결이 더 오래
점유되기 때문이다. 조건은 세 측정 모두 같으므로 비교에는 영향이 없다.

## 트레이드오프 정리

| 방식 | 정합성 | 성능 | 구현 복잡도 | 한계 |
|---|---|---|---|---|
| 나이브 | 재고 초과 발생 (+7~8건) | TPS 819 | 없음 | 쓸 수 없다 |
| 비관적 락 | 재고 정확 (0건) | TPS 218 (-73%) | 낮음 — 기존 모델에 락만 얹으면 된다 | 같은 쿠폰 요청이 완전히 직렬화된다. 잠글 대상을 잘못 고르면 gap lock 데드락 |
| 낙관적 락 | 재고 정확 (0건) | TPS 114 (-86%) | **높음 — 도메인 모델 변경을 요구한다** | 경합이 잦으면 재시도가 폭증한다. 이 시나리오에는 부적합 |
| unique 제약 | 중복만 차단, 재고는 못 막음 | 쓰기 경로에 비용 추가 | 낮음 — 마이그레이션 한 줄 | 위반 시 예외가 나간다. API 응답 설계는 별도 문제 |

**낙관적 락의 구현 복잡도가 높은 이유**는 코드 줄 수가 아니다.
발급 수가 `coupon_issue`의 행 개수로만 표현되면 `Coupon` 행에는 걸 버전이 없다.
`issued_quantity` 컬럼을 추가해 재고 상태를 행 안으로 옮겨야 낙관적 락이 성립한다.
그 순간 재고의 진실의 원천이 둘(컬럼과 행 개수)이 되고, 둘이 어긋나지 않는지
검증할 책임이 생긴다.

비관적 락은 이런 변경 없이 기존 모델 위에 락만 얹으면 됐다.
